# ESP32-C3 development target, 0.34

RF2 now has a separate native cross-compiler that emits RV32 machine code, ELF32 and RAM-resident Espressif boot images. RF2-generated programs boot through the ESP32-C3 ROM and SPI-flash model in Espressif QEMU and communicate through its UART model. **No physical board or temperature sensor has been tested.**

The compiler runs on Apple Silicon macOS. Its output targets ESP32-C3; these are different roles. This does not add an x86 host compiler, Linux application target, Arduino-wide compatibility or support for every RF2 systems feature.

## Build and run

Use the [native development bundle](../dist/0.34-candidate/README.md), or explicitly build the cross-compiler from source:

```sh
python3 tools/build-embedded.py /absolute/path/to/qualified-mac-rf2c new-build
./new-build/rf2-esp32c3 examples/esp32c3/uart-smoke.flow new-uart
```

The source build controller extracts reviewed lexical/module/SHA helpers from the canonical Mac compiler and combines them with `native/embedded/compiler.flow`. Python orchestrates this development build; it does not emit target instructions or package target images. The resulting native executable needs no Python, Node, C/C++, assembler or linker at runtime. It writes `new-uart.elf`, `new-uart.bin` and `new-uart.map`, refusing existing files and symlinks. Output I/O failure after publication starts may leave partial files; this is not a transactional three-file publish service.

## Bounded embedded language

```rf2
profile RF2_ESP32C3_V1
fn main()
 do store32(0x60000000,82)
 return 0
end
```

This tiny example writes an ASCII byte to the ROM-configured UART FIFO. The complete [UART example](../examples/esp32c3/uart-smoke.flow) checks FIFO availability with a bounded poll. The [echo application](../examples/esp32c3/uart-echo.flow) reads and writes a byte and returns a timeout error if none arrives.

The new profile supports unsigned 32-bit scalar functions, up to four parameters, optional `u32` annotations, `let`, `set`, `do`, `return`, nested `if`/`else` and `while`, forward helper calls and checked local module imports. It supports integer literals, unsigned comparisons, bitwise operations and word arithmetic. Add/subtract/multiply wrap at 32 bits. Shifts use the low five bits of the shift amount. Division and remainder follow RV32 unsigned semantics, including quotient `0xffffffff` and remainder equal to the dividend for a zero divisor. This differs from the existing Mac systems profile's zero-division rule; cross-profile code must not assume identical implicit word/division semantics.

`load8`, `load32`, `store8` and `store32` are explicit trusted raw memory/MMIO operations. They do not establish pointer validity, alignment safety, peripheral permission, process isolation or a sandbox. This profile has no strings, floating point, heap collections, structured results, ISR ABI, operating-system calls or arbitrary library compatibility. Unknown effects/types, oversized literals, invalid scopes and recursive calls refuse.

| Resource | Current bound |
| --- | ---: |
| Functions | 64 |
| Parameters per function | 4 |
| Scalar local slots per function | 64 |
| Acyclic call depth | 16 |
| Statement-block depth | 16 |
| Nested expression temporary slots | 32, each reserving 16 aligned bytes |
| Fixed function frame | 272 bytes |
| Generated code | 65,024 bytes |
| Largest admitted ROM image including digest | 65,104 bytes |

The expression and frame bounds imply at most 12,544 bytes along an admitted 16-deep call chain, below the reserved 16 KiB stack region. Raw writes outside the language frame discipline can still corrupt memory. Existing shared source/token/module limits apply to the frontend; these are finite compiler budgets, not an arbitrary-program proof.

## Boot and memory contract

Code loads at IRAM `0x40380000`. Startup clears machine-mode interrupt enables, sets SP to `0x3fcc0000`, calls argument-free `main`, then loops at entry+24 after return with `a0` preserving the return value. No interrupt handlers are installed. The code region's DRAM alias does not overlap the reserved stack region under the documented bounds.

The compiler directly writes ELF32/RISC-V and a single-segment ESP image for chip ID5, DIO/40 MHz/4 MiB header settings, XOR checksum, padding and appended SHA-256. The digest detects corruption; it does not authenticate a publisher or implement Secure Boot. The image is a direct ROM-loaded RAM program at flash offset0, not an ESP-IDF application partition with OTA, flash encryption or a general second-stage bootloader.

Board examples inherit UART0 baud, clock and pin initialization from the ROM loader. They do not independently initialize the whole clock tree, radio, watchdog or every peripheral. The current C3 DevKitM-1 contract and GPIO4/5 sensor wiring are in [board.json](../examples/esp32c3/board.json). The I2C delay loop is not calibrated bus timing. No flashing tool is automatically invoked.

## Temperature driver and failures

[TMP102 source and instructions](../examples/esp32c3/README.md) implement a read-only normal-mode sensor query using open-drain GPIO4/SDA and GPIO5/SCL with external pull-ups. The protocol has bounded SCL waits, ACK/NACK handling, repeated start, stop, configuration/raw-format checks, line release and explicit error returns. Register-pointer writes select a read register; the example does not reconfigure sensor operating modes.

Successful values render signed Celsius with four exact decimal places alongside the raw register. The sensor's resolution is not a claim about its physical accuracy. Sensor acquisition errors take precedence over successful UART output. That application-status gap was found during review and corrected before the final source freeze.

Tests use three distinct evidence levels:

1. **Actual ESP32-C3 QEMU ROM/SPI/UART execution:** generated firmware boots; UART TX/RX and timeout cases execute. With no sensor attached, the real board application reports its modeled GPIO clock failure and preserves the sensor error in `a0`.
2. **Scripted bus models:** unchanged RF2 protocol/formatting functions execute against supplied GPIO responses, with independent expected line traces, values and failure outcomes. A model temperature is never labelled a physical reading.
3. **Physical board:** unverified. Electrical pull-ups, voltage, pin multiplexing, bus timing, sensor calibration, power/reset and watchdog behavior still require identified hardware.

A disconnected wire cannot always be distinguished from a valid high bus level. TMP102 has no general end-to-end data-integrity guarantee supplied by this driver. Tests retain the case where data has completed but subsequent high line samples cannot prove a target remains attached. Do not claim universal disconnect detection.

## Qualification

The [qualification index](ESP32C3-0.34-QUALIFICATION.json) binds exact compiler, source, emulator and report identities. Independent qualification compared every emitted instruction in four images with an official GNU RISC-V assembler: **16,147 words**, including startup CSR instructions. Four actual ROM-boot programs exercise **176 arithmetic assertions**, control flow, memory, evaluation order and call frames. Invalid programs and existing/symlink output controls refuse. Monitor observations verify returned PC, restored SP, return value and disabled machine interrupts.

The [UART controller](ESP32C3-0.34-UART.json) executes four actual TX/RX/timeout cases. The [host protocol model](ESP32C3-0.34-PROTOCOL.json) passes464 controls; the [RV32 protocol model](ESP32C3-0.34-RV32-MODEL.json) also executes positive25C/negative25C/NACK/stuck-clock cases on the new target, substituting only GPIO responses. These are scripted temperatures.

These are local software controls. GNU tools and Espressif QEMU are independent development oracles, not RF2 runtime dependencies. The initial numeric test generator exceeded the legitimate code budget; the retained failure was fixed by sharing its test-report helper, not by widening the compiler limit. Apple Clang lacked the required RISC-V assembler backend, so it was not presented as the instruction oracle.

The stable nine-tool MCP runtime remains unchanged. Its official SDK exchanges pass, and a direct boundary check rejects embedded MMIO source before successfully executing a subsequent bounded computation. No compile/flash/raw-GPIO authority was added to MCP.

No physical-hardware, timing, speed, energy, Wi-Fi, radio, production readiness or AI-token advantage is claimed. Before physical deployment, identify the exact board/sensor, preserve its existing firmware where possible, review its security/flash state, then qualify boot, UART, reference temperature readings, missing-device handling and reset behavior.
