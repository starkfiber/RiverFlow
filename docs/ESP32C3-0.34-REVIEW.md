## Machine code and image evidence

An independently written decoder converts every emitted instruction word in the four positive firmware programs into explicit RISC-V assembly. Official Espressif GNU binutils 2.45 reassembles all 16,147 words with RV32IM plus the startup Zicsr instructions, ILP32 ABI, no compressed instructions and no relaxation. Its output matches the RF2 bytes exactly. The decoder does not establish source-level correctness by itself: Python-calculated arithmetic and actual QEMU behavior supply separate selected semantic oracles.

Each ELF independently passes ELF32 little-endian, executable type, EM_RISCV 243, aligned single RX load segment, entry/load address `0x40380000`, exact file/memory size and payload checks. The Espressif RAM image has chip ID 5, one matching segment, zero padding and the XOR checksum seeded by `0xEF`. Its appended SHA-256 covers the image through that checksum and matches the independently computed digest. These integrity hashes are not secure-boot signatures or authenticated firmware approval.

The image layout checks follow Espressif's [firmware image format specification](https://docs.espressif.com/projects/esptool/en/latest/esp32c3/advanced-topics/firmware-image-format.html). Tool provenance is pinned to the official archive and its verified SHA-256, with individual extracted executable hashes in the oracle manifest.

## Actual execution, not a register model

All four firmware programs boot through Espressif QEMU's ESP32-C3 ROM and a complete 4 MiB emulated SPI flash image. These are not host-side instruction interpretation or mocked UART register tests. UART serial logs contain the firmware success tokens and no checksum/SHA warning. QEMU monitor snapshots show return to `0x40380018`, restored stack pointer `0x3fcc0000`, result register a0 equal to zero and machine interrupts disabled. The corpus therefore verifies the return path as well as early UART output.

The tested programs are:

1. UART smoke: direct FIFO output from native RF2-generated instructions.
2. Numeric corpus: 176 runtime assertions across wrapping add/subtract/multiply, unsigned division/remainder, bitwise operations, masked shifts and unsigned comparisons. Cases include zero, maximum u32, the sign-bit boundary, shift counts 31/32/33, deterministic fresh operand pairs, architectural division by zero and remainder by zero.
3. Control/memory/calls: loop accounting, conditional branches, forward calls, four nested side-effecting arguments with left-to-right evaluation, u32 store/load, little-endian byte reads and a byte update that preserves neighboring bytes. Its scratch RAM is separate from code and stack storage.
4. Call frames: eight nested helper frames, each with four parameters and sixty named locals. Caller locals remain intact after the deeper call; the final independently calculated sum matches, followed by restored SP and normal main return.

The positive images contain 804, 24,972, 6,504 and 32,308 code bytes respectively. These are code-size observations, not speed measurements.

## Refusal evidence

Twenty-two malformed or unsupported programs refuse before producing any `.elf`, `.bin` or `.map` output. Cases cover the wrong machine profile, u32 decimal/hex overflow, unknown function/effect/local, direct/mutual recursion, a 17-function call path, duplicate function names, wrong call arity, five parameters, 65 local slots, branch-local use after lifetime, self-initialization, reserved MMIO intrinsic redefinition, absent main, main parameters, missing final root return, floating point and strings. The host syscall spelling is refused both with excessive arguments and with an otherwise admitted argument count, avoiding an arity-only false conclusion.

Existing ELF, image and map files remain byte-identical when compilation refuses. Previously created sibling outputs are cleaned up in the tested refusal paths. An existing image symlink and its target remain intact, with no partial ELF/map left behind. This is finite local file-publication evidence, not a race-proof or filesystem containment guarantee.

## Failed approaches retained

Apple clang 21 accepted a RISC-V target option at the frontend but its installed assembler backend did not support RISC-V. The attempt failed with an unknown RISC-V option/triple. No Apple-clang encoding proof is claimed. The replacement is the official Espressif GNU assembler, extracted locally after archive hash verification. Initial partial extraction reached wrapper binaries that required separately named backend executables; extracting those official companions resolved that developer-tool setup error.

The first numeric test generator duplicated long error UART strings in every case and legitimately exceeded the compiler's 65,024-byte code budget. That refusal is retained in `artifacts/sprint-034/review/embedded-1794594131991315000/failure.json`. The harness was changed to call a shared failure helper; the 176 assertions and result oracle were retained. This was a test-fixture size problem, not a compiler correctness defect. The v5 positive UART result is historical; the final campaign uses only v6 and verifies its unchanged compiler hash.

No implementation defect was found by this particular campaign. That statement does not invalidate faults found elsewhere or establish absence of bugs.

## Remaining boundaries

No ESP32-C3 board was attached or flashed. The host's serial devices are not proof of MCU presence. GPIO electrical behavior, physical I2C sensor transactions, timings, power, watchdog longevity, brownout behavior, interrupt handling and radio behavior remain unqualified here. Parent/board-agent peripheral and injected-bus tests are distinct evidence and must retain their own scopes.

The trusted source profile permits raw memory/MMIO. It does not sandbox register addresses or provide general memory safety. This campaign does not establish Arduino/ESP-IDF compatibility, Xtensa ESP32/S2/S3 output, other architectures, Wi-Fi, Bluetooth, USB, RTOS scheduling, heap collections or text libraries on the MCU. The generated file is a simple ROM-loaded RAM program, not a complete ordinary ESP-IDF partitioned application.

The finite maximum-depth refusal and eight-deep frame execution do not exercise every possible worst-case expression/call-stack combination. Physical RAM bounds, full stack stress and longer-running peripheral reliability remain additional acceptance gates. No performance, energy, AI-token or universal Python/C/assembly equivalence claim follows. Existing nine bounded MCP tools remain a separate host-runtime contract and do not gain arbitrary embedded source execution from this review.
