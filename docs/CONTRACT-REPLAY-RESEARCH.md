# Replay capsules, adversarial findings and measured cost

Research continuation, 12 November 2026. The application remains a candidate built with RF2 0.17. The native compiler and public release assets are unchanged.

## What changed

The RF2 runner can now export a self-contained replay capsule and read it in a fresh process:

```sh
python3 tools/build-contract.py output/bin/rf2-contract --opt
output/bin/rf2-contract capsule examples/evidence-contract/demo.plan > demo.rf2c
output/bin/rf2-contract replay demo.rf2c
```

RF2C1 has exactly seven whitespace-separated tokens: `RF2C1 source SOURCE64 receipt RECEIPT64 plan PLANHEX`. The source and receipt are exactly 64 lowercase hex characters each. The plan is the exact original byte sequence encoded as lowercase hex, at most 8192 decoded bytes. The capsule file is capped at 18000 bytes. Only ASCII space, tab, CR and LF separate tokens. Odd hex lengths, unsupported versions, stale source identities, extra tokens and receipt mismatches refuse. Whitespace between outer tokens is deliberately unbound; whitespace inside the decoded plan is bound by its hash.

The normal JSON report is unchanged. Capsule export uses the same exit status as the transformation: a valid capsule of an overflow refusal is emitted with a nonzero status. Replay reproduces that failure witness and original output. An invalid plan produces an error, not a valid capsule. A capsule includes input data in reversible form: do not publish private contents because they look like hexadecimal. The format is not encryption, a signature or remote execution attestation.

## A real input hang and its correction

An idle named pipe with no writer blocked the original reader at open. A controlled baseline invocation exceeded its one-second test timeout and was terminated. The reader now opens with Darwin O_NONBLOCK and refuses this fixture without waiting for a writer. Regression tests exercise ordinary, export and replay entry points in both build modes with a two-second process timeout. This removes the observed idle-FIFO wait; it does not establish deadlines for every device, remote filesystem or arbitrary system call.

## Negative controls that matter

Two isolated mutation builds changed XOR to OR in both the reference and candidate. For byte 3 and operand 1, both paths returned 3 and code 0; the independent expected XOR result is 2. The error was accepted in default and optimized modes. Agreement is conditional on at least one correct specification/implementation path. It cannot establish correctness against a common defect. The production engine was not changed to OR.

A separate test changed a plan and independently recomputed its unsigned receipt. Replay accepted it, as expected for a consistency check. Therefore a fixed trusted digest detects a changed payload, while a payload and attacker-supplied replacement digest do not authenticate a sender. Do not call these receipts tamperproof or approved. No cryptographic signature or trusted external verifier has been implemented.

## Why the fused candidate is eligible

For a uniform pointwise map F and reversal R, `R(F(x))[i] = F(R(x))[i]`: both evaluate the same element function at `x[n-1-i]`. Also `R(R(x)) = x`. The candidate therefore applies the original ordered pointwise functions to an index selected by reversal parity. It does not commute ADD with XOR. Checked ADD is partial: the reference must first complete successfully, otherwise its first failure witness is returned and candidate publication is skipped. This is an argument for the admitted operations, not a machine-checked equivalence proof.

This argument fails for position-dependent maps. With x=[0,0] and F(x)[i]=x[i]+i, R(F(x))=[1,0] but F(R(x))=[0,1]. Such an operation cannot reuse this fusion rule without a new proof condition and tests.

## Verification cost, with the simpler baseline retained

The benchmark compiles a private reference-only variant and the production two-path engine with the same native compiler and --opt. Both receive identical generated bytes and ordered transforms. Full-domain and adversarial correctness checks are separate. The benchmark checks a running output accumulator, final byte sum, status and expected abstract work. It uses two warmups and 21 randomized-order trials per path. Timing includes process launch, initialization, resets and observation overhead; it is not isolated instruction cost. The reference-only variant deliberately lacks candidate-disagreement detection. It is never exposed as a production bypass.

Dual validation cost 1.30 to 1.85 times the reference-only harness median in the confirmation run. This measures a reliability/verification tradeoff, not a speed advantage. Raw observations, ranges, source/binary hashes and trial order seed are in [the measurement record](CONTRACT-OVERHEAD-MEASUREMENTS.json). The earlier short run was noisy; an exploratory longer run overlapped other owned tests. Both remain in local artifacts and are not used for this table. The confirmation ran after those tests completed, but other host activity and scheduling were not controlled. No confidence interval, energy measurement, AI provider-token experiment, cross-machine replication or general C/Python/Java performance conclusion is established.

## Executed coverage

The final regressions recorded 554 engine cases,290CLI cases and 1262 capsule/metamorphic/boundary cases. The exhaustive one-byte experiment covered 131072 distinct ADD/XOR input/operand combinations in each native mode, giving 262144 observations, including 32640 overflow refusals per mode. A preserved tail sentinel and complete Run fields were checked. This is not exhaustive verification of multistep plans or arbitrary 128-byte states. Four common-defect experiment runs included two deliberately wrong accepted outputs; these are reported as a limitation. The capsule count includes two controls that intentionally demonstrate acceptance of a recomputed unsigned receipt, not authentication success.
