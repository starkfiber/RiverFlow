# What RF2 must earn

RF2's product direction is a readable route from intent to a working application, with explicit authority, recoverable failures and native delivery. A compiler optimization is evidence about that optimization. It is not evidence that a whole product is easier, cheaper, universally faster or safer.

## Four experiences, one implementation contract

| Audience | Journey to make concrete | Observable acceptance |
| --- | --- | --- |
| Developer | Write, check, build, run, diagnose, change | A fresh checkout can reproduce the tutorial; useful source errors; tested library contracts; unchanged programs retain behaviour |
| AI tool author | Discover capabilities, propose bounded inputs, inspect errors, retry | Machine-readable schemas, explicit authority and limits; negative inputs refuse without unintended changes; actual task traces |
| Learner | Predict, run, see result, modify, understand mistake | A short worked example with expected outcomes and explanations; actual learner observations before claiming learnability |
| Business owner | Specify a workflow, inspect results, install, operate and recover | A completed task, clear failure handling, installation and support costs; independent user acceptance before claiming business value |

These experiences are objectives, not completed user studies. The native Number Lab demonstrates an interactive learning interface. It does not establish educational effectiveness. Nine MCP tools expose bounded operations; they do not provide an autonomous software company or embedded model.

## The adoption experiment

Select a defined application with a frozen feature list and independent acceptance tests. Include normal use, invalid input, interruption, recovery and a fresh-machine installation. Compare complete tasks against a mature stack selected for that application. Preserve prior experience, tool versions, prompts, model usage receipts, retries, human intervention and unresolved defects. Measure build and execution separately. A shorter program or a faster kernel cannot stand in for the whole experiment.

Report successful features, developer time, actual model usage, failed attempts, package size, installation steps and measured execution. Retain reference-library wins and RF2 losses. Without controlled trials, development here supplies engineering evidence only.

## Foundation work that serves the experiment

1. Useful diagnostics: point to an honest location, explain the actual failure, never fabricate an imported source line.
2. Reusable data/text/collection interfaces with explicit bounds and failure contracts.
3. Modules and version compatibility that let developers reuse supported code predictably.
4. Correctness comparisons, fuzzed boundary inputs, clean-build oracles and deterministic reproducers.
5. Explicit effect and resource ownership rules across local CLI, graphical UI and MCP routes.
6. Packaging and multiple actual targets, each qualified independently.

Direct ARM64 emission gives RF2 control over instruction selection on its supported target. It does not rewire fabricated transistors or prove superiority to established compilers. Research-inspired mechanisms must have executable contracts and discriminating tests. Independent agents can find defects; their agreement is not independent academic approval or a security certification.
