# Arduino and MCP reference review

This review informs RF2's ESP32-C3 development. It is a static inspection of selected pinned sources, not an execution audit, complete repository review or Arduino compatibility claim. No Arduino MCP tools are attached in this chat. No server, CLI, dependency installer or hardware port from these projects was run.

| Repository and reviewed revision | Inspected source | Lesson used or retained |
| --- | --- | --- |
| [hardware-mcp/arduino-mcp-server](https://github.com/hardware-mcp/arduino-mcp-server/tree/c020098a05b0d259320df2756fde09e7ca6fecc0) | README, `src/serialSessions.ts`, `src/boardReference.ts` | Explicit session state, exclusive port ownership, bounded buffers/expiry and board-specific metadata are useful patterns. RF2's emulator controller retains explicit process ownership, output limits and cleanup. A board reference is not an observation that wiring is safe. |
| [amahpour/arduino-mcp-server-simple](https://github.com/amahpour/arduino-mcp-server-simple/tree/fa3170d3f67c6a3915c4fe56221d992d923a1e13) | README, `arduino_mcp_tool/__init__.py` | Compile/upload are separate actions and subprocesses use argument arrays. Its inspected CLI helper waits for completion without an explicit deadline; RF2 controllers retain their own subprocess and observation deadlines. RF2 does not adopt automatic board selection as device authorization. |
| [niradler/arduino-mcp](https://github.com/niradler/arduino-mcp/tree/dae94d3bfb5aac20942af785d504b74b5395884f) | README, CLI wrapper, serial manager, server | Discoverable board resources and compile/monitor separation aid users. The inspected CLI execution method has no timeout despite its installation probe having one. The serial manager's bounded line count is not an exact byte-memory bound. These are review leads, not reproduced upstream vulnerabilities. |
| [espressif/arduino-esp32](https://github.com/espressif/arduino-esp32/blob/3ed7b779f2b4c797b3512f3fc10a7a978a78fb18/cores/esp32/esp32-hal-timer.c) | `cores/esp32/esp32-hal-timer.c` | Explicit timer start/stop, clock-resolution handling and alarm configuration show the scope of a mature API. RF2 adds a smaller foreground SYSTIMER/TIMG0 contract and does not claim interrupt alarms, GPTimer handles or API parity. |

The [source manifest](ESP32C3-TIMERS-SOURCES.json) records exact URLs, revisions and SHA-256 values. External source files are retained locally for review, not redistributed in RF2's native package. No implementation or dependency is adopted from the MCP servers. Their Node/Python/Arduino CLI dependencies are not RF2 user runtime requirements.

RF2's current MCP surface remains the nine existing bounded computational tools. Raw compilation, device selection, flashing and serial-device access remain outside it. A future embedded MCP service should separate read-only board descriptors and captured evidence from explicit compile, emulator and physical-device operations. Candidate requirements are immutable artifact hashes, caller-selected board/port identity, exclusive sessions, duration/output limits, cancellation and cleanup receipts. Those additional tools are a roadmap, not shipped capability.

The RF2, WhatIF and Reverse Lab skills guided this work. The attached WhatIF explore tool supplied scenario/invariant discipline; it is not an embedded runner. Its source heuristic inspected selected Python controllers and excluded `.flow` sources. Actual firmware qualification used RF2 compilation and vendor QEMU through the checked-in controller. No independent human council, autonomous hardware capability or third-party MCP execution is claimed.
